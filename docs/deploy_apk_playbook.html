Deploy APK(s) to the Fleet
フリートへの APK 配信手順
KAGAMI / Tin Drum
Use when pushing a new show-app build to every device. Run from the show laptop, on the show's WiFi.  ·  新しいショーアプリのビルドを全デバイスへ配信するときに使用します。ショー用ラップトップから、ショーの WiFi に接続して実行します。
⚑ Set the show first — Red or Blue
Every command below acts on whichever show this laptop is set to. Set it once, then glance at the Show / SSID banner each command prints — wrong show means wrong fleet.
# Red — Studio A cabinets, SSID KAGAMI ./ml_show.sh use KAGAMI # Blue — flight cases, SSID KAGAMI-BLUE ./ml_show.sh use KAGAMI_BLUE
⚑ 最初にショーを設定 — Red か Blue
以下の各コマンドは、このラップトップが設定されているショーに対して実行されます。一度設定し、各コマンドが表示する Show / SSID バナーを毎回確認します — ショーを間違えると対象フリートを間違えます。
# Red — Studio A cabinets, SSID KAGAMI ./ml_show.sh use KAGAMI # Blue — flight cases, SSID KAGAMI-BLUE ./ml_show.sh use KAGAMI_BLUE
On-screen text stays in English.  画面に表示される文字は英語のままです。 Commands, file names, and terminal output are intentionally left in English in both columns — that is exactly what appears in Terminal and on the device, so it stays matchable. Only the explanation is translated. コマンド・ファイル名・ターミナルの出力は、両方の列で意図的に英語のままにしています。Terminal やデバイスに表示されるものと一致させるためです。説明文のみを翻訳しています。 （日本語は翻訳者レビュー前の暫定版です。）
Set the show first (box above). On the dev branch, prefix each command with ML_DEV_TEST=1 and skip ./update.sh.  ·  先にショーを設定します（上のボックス）。dev ブランチでは各コマンドの先頭に ML_DEV_TEST=1 を付け、./update.sh は省略します。
Before you start 開始前の準備
1
Stage the new APK in builds/
Place the new show-app APK in builds/ and remove the old version. install pushes exactly the file you name, so this is mostly hygiene — make sure the old build isn't lying around.
新しい APK を builds/ に配置
新しいショーアプリの APK を builds/ に置き、古いバージョンを削除します。install は指定したファイルだけを配信するため、これは主に整理のためです — 古いビルドが残っていないことを確認します。
2
Confirm the expected version (supervisor)
The supervisor sets SHOW_EXPECTED_APK in the show config to the new version, so status goes green after the deploy. Operators do not edit this.
期待バージョンの確認（スーパーバイザー）
スーパーバイザーがショー設定の SHOW_EXPECTED_APK を新しいバージョンに設定します。これにより配信後の status が緑になります。オペレーターはこれを編集しません。
Deploy steps 配信の手順
3
Power up & confirm the network
Power on the cabinets. Confirm the AP broadcasts the show SSID and the laptop is on it (or wired to the same subnet). Give devices ~2 min to boot and join.
ipconfig getifaddr en0
Be on your show's SSID — KAGAMI (red) / KAGAMI-BLUE (blue), not the house wifi (check the macOS wifi menu). A returned address means you're connected.
電源を入れてネットワークを確認
キャビネット（cabinets）の電源を入れます。AP がショーの SSID を発信し、ラップトップが同じネットワーク（または同一サブネットの有線）に接続されていることを確認します。デバイスの起動と参加まで約2分待ちます。
ipconfig getifaddr en0
自分のショーの SSID に接続していること — KAGAMI（red）/ KAGAMI-BLUE（blue）、会場の wifi ではなく（macOS の wifi メニューで確認）。アドレスが返れば接続済みです。
4
Clear the update gate
Every command checks your toolkit matches everyone else's. Run this first — it pulls the latest and protects the shared fleet key.
./update.sh
If you see the red box Toolkit is out of date, you skipped this.
アップデートゲートを通過
各コマンドは、ツールキットが全員と同じバージョンかを確認します。最初にこれを実行します — 最新を取得し、共有のフリートキーを保護します。
./update.sh
赤いボックス Toolkit is out of date が出たら、この手順を飛ばしています。
5
Scan — run until the count stops growing
Build the device list. One pass undercounts a large fleet, so run it, then --append again until the number is stable.
./utilities/ml_scan.sh --yes ./utilities/ml_scan.sh --append --yes
Subnet line reads 172.16.40.0/22; count settles (≈183 for red) and stops growing.
スキャン — 台数が増えなくなるまで実行
デバイスリストを作成します。大規模フリートでは1回では台数が不足するため、実行後に --append を台数が安定するまで繰り返します。
./utilities/ml_scan.sh --yes ./utilities/ml_scan.sh --append --yes
subnet の行が 172.16.40.0/22、台数が安定（RED は約183）して増えなくなること。
6
Connect to the fleet
install only reaches devices that are adb-connected, so connect first. This also flags any device whose auth lapsed.
./ml_deploy.sh connect
Connected near the full count, Failed: 0. (port open, adb connect failed = that device needs re-auth.)
フリートに接続
install は adb 接続済みのデバイスにのみ届くため、先に接続します。認証が切れたデバイスもここで分かります。
./ml_deploy.sh connect
Connected が満台数に近く、Failed: 0。（port open, adb connect failed = そのデバイスは再認証が必要。）
7
Baseline status — the "before"
Confirm the fleet is healthy before changing anything. Because the expected version is already the new one, every device flags on the app column — that's expected, it's the proof you need the deploy. Look past it: OS, Kiosk, and settings should be green.
./ml_status.sh
App column shows the old version everywhere; everything else green. A device flagged on something other than the app is a real one to check.
ベースラインの status —「変更前」
変更前にフリートが健全か確認します。期待バージョンが既に新版のため、全デバイスがアプリ列で flag されます — これは想定どおりで、配信が必要な証拠です。それ以外を見ます: OS・Kiosk・設定が緑であること。
./ml_status.sh
アプリ列が全台 旧バージョン、それ以外は緑。アプリ 以外 で flag されたデバイスは、実際に確認すべきもの。
8
Install the new APK
Push just the new app to all connected devices, in parallel — a clean in-place upgrade. This is the heavy step: ~150 MB to every device over wifi. Even in ideal conditions this took ~25 minutes, and there's no progress bar — it will look frozen but isn't, so don't cancel it. (The version changes each release, so the command uses a v* wildcard — it installs whichever build is in builds/, which is why step 1 keeps just one there.)
# Red: ./ml_deploy.sh install builds/kagami-red-v*.apk # Blue: ./ml_deploy.sh install builds/kagami-blue-v*.apk
Goal: Success: <count>  Failed: 0. A few fail → re-run the same command. Many fail → re-run connect, then install.
新しい APK をインストール
新しいアプリのみを、接続済みの全デバイスへ並列で配信します — その場でのクリーンなアップグレードです。ここは重い手順です: 全デバイスへ wifi 経由で約150MB。理想的な条件でも約25分かかり、進捗バーはありません — 止まって見えても動いているので、中断しないでください。（バージョンはリリースごとに変わるため、コマンドは v* ワイルドカードを使い、builds/ にあるビルドをインストールします。だから手順1で1つだけにしておきます。）
# Red: ./ml_deploy.sh install builds/kagami-red-v*.apk # Blue: ./ml_deploy.sh install builds/kagami-blue-v*.apk
目標: Success: <count>  Failed: 0。数台失敗 → 同じコマンドを再実行。多数失敗 → connect を再実行してから install。
9
Reboot the fleet
The APK is on disk, but a headset may still be running the old version. Reboot relaunches every device on the new app and triggers the boot-time asset scripts. Use reboot, not a manual relaunch — it's the clean, deterministic path.
./ml_deploy.sh reboot
It fires and returns immediately. Devices take ~60–90s to come back — wait ~2 minutes before verifying.
フリートを再起動
APK はディスク上にありますが、ヘッドセットはまだ旧版を実行している場合があります。再起動で全デバイスを新アプリで起動し直し、起動時のアセットスクリプトも実行します。手動の再起動ではなく reboot を使います — クリーンで確実な方法です。
./ml_deploy.sh reboot
コマンドは即座に戻ります。デバイスの復帰には 約60〜90秒。確認の前に 約2分 待ちます。
10
Verify — the proof
Run status again. It re-probes and reconnects on its own — no need to connect again. The app column should flip to the new version, green.
./ml_status.sh
App column = new version (green); All-OK jumps to the full count. A few still offline = slow to rejoin; wait a minute and re-run.
確認 — 証拠
もう一度 status を実行します。自身で再プローブ・再接続するため、connect は不要です。アプリ列が新バージョン・緑に変わります。
./ml_status.sh
アプリ列が 新バージョン（緑）、All-OK が満台数に増加。数台が offline のまま = 復帰が遅いだけ。1分待って再実行。
Reading the results 結果の読み方
·
status and status --json are separate live reads
Each status run re-probes the whole fleet from scratch, so two runs minutes apart can differ — a device can be online in one and offline in the next. That's normal. --json is a separate run from the table, not the same data reformatted.
status と status --json は別々のライブ取得
各 status はフリート全体をゼロから再プローブするため、数分違う2回の実行で結果が異なることがあります — あるデバイスが片方で online、もう片方で offline になることも。これは正常です。--json は表とは別の実行であり、同じデータの整形ではありません。
·
Don't trust the flags on a device that keeps dropping off
A device that's intermittently unresponsive can return partial reads that show up as false setting-flags. If one device flags oddly, verify on the device before acting. If it keeps dropping but is powered and running, it has likely lost WiFi-ADB — bench it (USB re-provision or flash) rather than chase the flags.
不安定なデバイスの flag は鵜呑みにしない
断続的に応答しないデバイスは、部分的な読み取りにより誤った設定 flag を返すことがあります。1台だけ不自然に flag される場合は、対応前にデバイス側で確認します。電源が入って動作しているのに頻繁に落ちる場合は WiFi-ADB を失っている可能性が高く、flag を追うより、ベンチで対処（USB で再プロビジョンまたはフラッシュ）します。
