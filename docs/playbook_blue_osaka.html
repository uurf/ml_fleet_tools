Blue Osaka Operator Playbook
青ショー 大阪 オペレーター手順書
KAGAMI / Tin Drum
Devices: 24 PGH-flashed + ~180 HK ≈ 204 total (HK count + DOA triage TBD — supervisor confirms final number on site) · WiFi: KAGAMI-Blue (TBD — confirm with supervisor) · Show context: KAGAMI_BLUE
対象機: PGH フラッシュ済24台 ＋ HK 約180台 ≈ 合計204台（HK の実数・初期故障数は現地でスーパーバイザーが確定）・WiFi: KAGAMI-Blue（仮 — スーパーバイザーに確認）・ショー: KAGAMI_BLUE

Japanese pass is a first draft by the toolkit author, not a native speaker. Tin Drum bilingual staff should correct anything that reads awkwardly before this is handed to operators. ネイティブ翻訳ではないため、Tin Drum の日本語スタッフが必要に応じて修正してください。
Two phases. BLUE devices weren't fully provisioned for this show before shipping (HK 180) or were provisioned for KAGAMI Red (PGH 24). Phase A is a per-device USB-bench precursor that joins them to the BLUE WiFi and enables WiFi ADB. Phase B is the same fleet flow as the Red playbook, run once Phase A is complete on every device.
2フェーズ構成。BLUE 対象機は出荷時にこのショー向けプロビジョン未完了（HK 180台）、または KAGAMI Red 用にプロビジョン済（PGH 24台）です。フェーズ A は各デバイスに USB 接続して BLUE WiFi に接続・WiFi ADB を有効化する個別作業。フェーズ B は全機がフェーズ A を完了した後に実行する、Red 手順書と同じフリート作業です。
0 · Before you start (one-time per laptop) 0・開始前の準備（ノートPCごとに1回）
Toolkit installed and up to date
Run cd ~/Developer/ml_toolkit && ./update.sh. If you haven't installed yet, follow docs/setup_checklist.html first.
ツールキットをインストール済み・最新版である
cd ~/Developer/ml_toolkit && ./update.sh を実行。未インストールの場合はまず docs/setup_checklist.html を参照してください。
Shared Fleet ADB key in place
Supervisor provides adbkey_kagami_fleet on a USB drive. Copy to ~/Developer/ml_toolkit/authorized_keys/ and re-run ./install.sh. Look for "Fleet ADB key installed".
共有フリートADBキーが設定済み
スーパーバイザーから配布される USB ドライブ内の adbkey_kagami_fleet を ~/Developer/ml_toolkit/authorized_keys/ にコピーし、再度 ./install.sh を実行。"Fleet ADB key installed" の表示を確認してください。
Create the KAGAMI_BLUE show config
If your laptop doesn't yet have shows/KAGAMI_BLUE.conf, run ./ml_show.sh init. Answer the prompts with the values supervisor provides:
Show id: KAGAMI_BLUE
SSID: KAGAMI-Blue (confirm with supervisor)
Password: KAGAmius (confirm)
Security: wpa2
Show package, brightness, data dir, expected APK/OS, kiosk version: ask the supervisor running the deploy for current values
Sheets URL: ask the supervisor for the BLUE Apps Script Web App URL
KAGAMI_BLUE のショー設定を作成
shows/KAGAMI_BLUE.conf がまだ存在しない場合、./ml_show.sh init を実行。スーパーバイザー提供値を入力します:
Show id: KAGAMI_BLUE
SSID: KAGAMI-Blue（スーパーバイザーに確認）
Password: KAGAmius（確認）
Security: wpa2
ショーパッケージ・明るさ・データディレクトリ・期待 APK/OS・キオスクバージョン: デプロイ担当のスーパーバイザーに最新値を確認
Sheets URL: スーパーバイザーに BLUE Apps Script Web アプリ URL を確認
Set active show to KAGAMI_BLUE
./ml_show.sh use KAGAMI_BLUE, then ./ml_show.sh — should report Active show: KAGAMI_BLUE.
アクティブショーを KAGAMI_BLUE に設定
./ml_show.sh use KAGAMI_BLUE を実行後、./ml_show.sh で Active show: KAGAMI_BLUE を確認。
Show APK and kiosk APK in builds/ when available
Supervisor places the latest BLUE show build and kiosk build in ~/Developer/ml_toolkit/builds/. Phase A can proceed without them — if no APKs are present, Phase A is settings + WiFi only. Phase B re-deploys whenever new builds arrive.
ショー APK・キオスク APK を builds/ に配置（入手次第）
スーパーバイザーが最新の BLUE ショービルドとキオスクビルドを ~/Developer/ml_toolkit/builds/ に配置します。フェーズ A は APK なしでも実行可能（設定 + WiFi のみ）。新ビルド到着時はフェーズ B で再デプロイ。
KAGAMI-Blue WiFi broadcasting in the room
SSID: KAGAMI-Blue · Password: KAGAmius (TBD — confirm). Your laptop's WiFi must also be on this SSID for Phase B. Phase A is USB so it doesn't depend on WiFi, but devices need the WiFi to be live when they're powered on.
会場で KAGAMI-Blue WiFi が稼働している
SSID: KAGAMI-Blue・パスワード: KAGAmius（仮 — 確認）。フェーズ B ではノート PC もこの SSID に接続が必要。フェーズ A は USB 接続のため WiFi に依存しませんが、デバイス起動時には WiFi が稼働していることが必要です。
Phase A
USB bench: join BLUE WiFi + enable WiFi ADB
フェーズ A
USB ベンチ: BLUE WiFi 接続＋WiFi ADB 有効化
Throughput. ~5 minutes per functional device including the Allow tap and the manual checklist. With 8 operator stations (4 operators × 2 laptops), ~200 functional devices take ~2.5 hours. One device per laptop at a time. If a HK unit won't boot or won't respond over ADB, set it aside and report to the supervisor — don't burn bench time on hardware faults.
処理速度の目安。1台あたり約5分（許可ダイアログ＋手動チェックリスト込み）。8 ステーション（4 オペレーター × 2 ノートPC）で 約200台＝合計約2.5時間。1ノートPCあたり同時1台。HK の機体が起動しない、または ADB が応答しない場合は脇に置きスーパーバイザーに報告してください — 故障機にベンチ時間を費やさない。
A · Per device (repeat across stations until every functional unit is done) A・各デバイスごと（全ステーション合計で全稼働機が完了するまで繰り返し）
Connect device to MacBook via USB-C
One device at a time per laptop. Plug the Compute Pack into your USB-C port.
デバイスを USB-C で MacBook に接続
1 ノート PC につき同時 1 台。Compute Pack を USB-C ポートに接続。
Check that the device powers on and shows up
Within ~10 seconds the device should boot and appear in adb devices. If it won't power on, or doesn't show up after a power-cycle and a different USB-C cable, set it aside in the DOA stack and pick up the next unit. Note the carnet/case number for the supervisor.
デバイスが起動し認識されることを確認
約10秒以内に起動し adb devices に表示されるはず。起動しない、または再起動・USB-C ケーブル交換後も認識されない場合は故障機スタックに脇置きし、次の機体へ。スーパーバイザー報告用にカルネ/ケース番号を控える。
Tap "Allow USB debugging" in the headset (first connect)
For HK devices (never seen this laptop before): a dialog appears in the headset on first connect. Put the headset on, check Always allow from this computer, tap Allow.
For PGH-flashed devices: dialog may not appear (fleet key already trusted). Either way, proceed when the device shows up in adb devices.
ヘッドセット内で「USB デバッグを許可」をタップ（初回接続時）
HK デバイス（このノート PC に初めて接続）の場合、初回接続時にダイアログが表示されます。ヘッドセットを装着し このコンピュータを常に許可 をチェック、許可 をタップ。
PGH フラッシュ済みデバイスはダイアログが表示されない場合あり（フリートキーが既に信頼済み）。adb devices でデバイスが認識されたら次へ進んでください。
Dismiss "USB Device Detected"
A second dialog appears on every connection regardless of authorization — just tap OK.
「USB デバイスを検出」を閉じる
認証状態に関わらず接続のたびに表示される2つ目のダイアログです。OK をタップしてください。
Run provision (with deploy if builds are ready)
If show + kiosk APKs are in builds/: ./ml_provision.sh --deploy. This applies settings, joins KAGAMI-Blue WiFi, runs the manual-headset checklist gate, installs APKs over USB, then enables WiFi ADB.
If APKs aren't ready yet: ./ml_provision.sh (no --deploy). Settings + WiFi + WiFi ADB only; APK install happens later in Phase B.
プロビジョンを実行（ビルドが揃っていればデプロイも）
builds/ にショー＋キオスク APK がある場合: ./ml_provision.sh --deploy。設定適用、KAGAMI-Blue WiFi 接続、ヘッドセット手動チェックリスト確認、USB 経由 APK インストール、最後に WiFi ADB を有効化します。
APK が未到着の場合: ./ml_provision.sh（--deploy なし）。設定 + WiFi + WiFi ADB のみ。APK インストールはフェーズ B で実施します。
Confirm the show — press Enter
Prompt: "Press Enter to continue, or S for other available show configurations:". Banner above must show Show: KAGAMI_BLUE. Press Enter.
ショーを確認 → Enter を押す
プロンプト "Press Enter to continue, or S for other available show configurations:"。上部バナーが Show: KAGAMI_BLUE であることを確認し、Enter を押します。
Enter device tracking info if prompted
If the script prompts for device number / case number / operator initials, fill them in. (Standalone Phase A may not prompt — that's fine.)
プロンプトが出たらデバイス追跡情報を入力
デバイス番号・ケース番号・オペレーターイニシャルの入力プロンプトが表示されたら入力。フェーズ A 単独実行ではプロンプトが出ない場合もあり、その場合は不要です。
Complete the manual-headset checklist gate
Script pauses at: "Press Enter when manual steps are complete...". While paused, complete the items in docs/headset_checklist.html — Display Override, Segmented/Global/Max Dimming, Compute Pack Standby = Off, OS Updater = Never. Then press Enter.
ヘッドセット手動チェックリストを完了
スクリプトが "Press Enter when manual steps are complete..." で一時停止します。停止中に docs/headset_checklist.html の項目を完了 — Display Override、Segmented/Global/Max Dimming、Compute Pack Standby = Off、OS Updater = Never。完了後 Enter を押す。
Note the device IP from the final output
The script prints Device IP: 10.x.x.x. Confirm the line WiFi ADB enabled on port 5555 appears. The USB connection drops here — that's expected, the device is on KAGAMI-Blue now.
最終出力からデバイス IP を記録
スクリプトが Device IP: 10.x.x.x を表示します。WiFi ADB enabled on port 5555 の行も確認。ここで USB 接続が切れるのは正常 — デバイスは KAGAMI-Blue に接続済みです。
Disconnect USB and move to next device
Stage the just-finished device aside (still powered on so it stays on the BLUE WiFi). Pick up the next device, return to step A1.
USB を外し次のデバイスへ
完了したデバイスは電源を入れたまま脇に置きます（KAGAMI-Blue WiFi に接続を維持）。次のデバイスを取り、A1 へ戻ります。
Phase A done across all stations? → Continue to Phase B.
全ステーションでフェーズ A 完了？ → フェーズ B へ進む。
Phase B
Fleet deploy + asset transfer
フェーズ B
フリートデプロイ＋アセット転送
Same as Red Phase B. Once every BLUE device is on the KAGAMI-Blue network and reachable over WiFi ADB, the rest is identical to the Red playbook — just with the BLUE show context active. New builds can be re-deployed at any time; the longest wait is the WiFi APK install, not flashing (we are not flashing on site).
Red のフェーズ B と同じ。BLUE 全機が KAGAMI-Blue ネットワーク上で WiFi ADB 到達可能になれば、以降は Red 手順書と同一です（ショーコンテキストが BLUE になるだけ）。新ビルドはいつでも再デプロイ可能。最大の待ち時間は WiFi 経由の APK インストールで、フラッシュではありません（現地ではフラッシュは行いません）。
B · Inventory the BLUE fleet on the network B・ネットワーク上の BLUE フリートを確認
Confirm devices are powered on and on KAGAMI-Blue
If devices were staged off after Phase A, power them on now. They auto-join KAGAMI-Blue WiFi from the credentials applied during Phase A.
全機が起動し KAGAMI-Blue に接続されていることを確認
フェーズ A 後に電源を切った場合は今ここで再起動。フェーズ A で設定された認証情報により KAGAMI-Blue WiFi に自動接続されます。
Scan the network for ML2 devices
./utilities/ml_scan.sh writes devices/KAGAMI_BLUE.txt. Confirm the count matches the supervisor's expected total (= 24 PGH + functional HK units that cleared Phase A). If short, power-cycle the missing devices and rescan with --append.
ネットワーク上の ML2 デバイスをスキャン
./utilities/ml_scan.sh が devices/KAGAMI_BLUE.txt を作成します。台数がスーパーバイザー確定の合計値（24 PGH ＋ フェーズ A 完了済の HK 稼働機）と一致することを確認。不足している場合は該当機を再起動し、--append で再スキャン。
C · Drift check C・ドリフトチェック
Run fleet drift check
./ml_provision.sh --fleet --check. Read-only audit. Phase A should have brought every device to the expected baseline — drift here usually means a device that was missed in Phase A or a settings change that didn't take.
フリート全体のドリフトチェック
./ml_provision.sh --fleet --check を実行（読み取り専用）。フェーズ A 後は基準値に揃っているはず — ドリフトが出た場合は、フェーズ A で漏れたデバイスか、設定が適用されなかったケースの可能性。
Auto-fix if drift is reported
./ml_status.sh --fix for stay-awake / BT / brightness drift. For anything else, USB-bench the offending device again (back to Phase A for that unit).
ドリフトが報告されたら自動修復
スリープ防止・BT・明るさのドリフトは ./ml_status.sh --fix。それ以外のドリフトは、該当機をフェーズ A で USB ベンチからやり直してください。
D · Deploy the BLUE show + kiosk APKs D・BLUE ショー APK＋キオスク APK のデプロイ
Confirm the BLUE builds are in builds/
ls -la ~/Developer/ml_toolkit/builds/*.apk. The BLUE show APK package name differs from Red — confirm with supervisor. The kiosk APK is shared between shows, but the kiosk versionName is per-show (BLUE's will be e.g. 1.0b).
BLUE 用ビルドが builds/ にあることを確認
ls -la ~/Developer/ml_toolkit/builds/*.apk。BLUE ショー APK のパッケージ名は Red と異なります — スーパーバイザーに確認してください。キオスク APK パッケージは共通ですが、versionName はショーごとに異なります（BLUE は 1.0b 想定）。
Start the deploy
./ml_deploy.sh deploy. Connects to every device in devices/KAGAMI_BLUE.txt. At the confirm prompt, banner must show Show: KAGAMI_BLUE — press Enter to proceed.
デプロイを開始
./ml_deploy.sh deploy を実行。devices/KAGAMI_BLUE.txt の全機に接続。確認プロンプトでバナーが Show: KAGAMI_BLUE であることを確認し、Enter を押します。
Select APKs and wait
Pick the APK numbers (e.g. 1 2), press Enter. The script installs, sets kiosk as home, persists, and reboots. Allow 5–15 minutes depending on build size + AP load. End state: Deploy complete. Devices are rebooting.
APK を選択し完了を待つ
APK 番号を入力（例: 1 2）、Enter を押す。インストール、キオスクをホームに設定、保存、再起動を実行。所要時間 5〜15分（ビルドサイズと AP 負荷次第）。終了表示: Deploy complete. Devices are rebooting.
E · Confirm fleet health via the dashboard E・ダッシュボードで全機の状態を確認
Wait ~45s for reboots to finish, then generate snapshot
./ml_status.sh --json > status/latest.json. Open fleet_dashboard.html and drag the JSON onto it.
再起動完了まで約45秒待ち、スナップショット生成
./ml_status.sh --json > status/latest.json を実行。fleet_dashboard.html を開き、JSON をドラッグ＆ドロップ。
Expected state at this point
Every BLUE device that cleared Phase A online; BLUE show APK + kiosk version matching shows/KAGAMI_BLUE.conf; no OFFLINE rows; no extraneous com.tindrum.* packages. Data folder rows still red (assets not loaded yet).
この時点での期待状態
フェーズ A を完了した全 BLUE 機がオンライン、BLUE ショー APK・キオスクバージョンが shows/KAGAMI_BLUE.conf と一致、OFFLINE 行なし、余分な com.tindrum.* パッケージなし。データフォルダ行はまだ赤（アセット未転送）。
Report any unexpected red rows
Note IPs of any devices showing wrong APK / kiosk / extraneous packages and hand to supervisor before proceeding.
想定外の赤行はスーパーバイザーへ報告
誤った APK・キオスク・余分なパッケージが検出された IP を記録し、次へ進む前にスーパーバイザーに報告。
F · Shut the fleet down for asset transfer F・アセット転送のため全機をシャットダウン
Shut down all devices
./ml_deploy.sh shutdown. Required for the timing-critical SSD load in Section G — the show APK only triggers its SSD copy on a fresh power-on with the SSD already attached.
全機をシャットダウン
./ml_deploy.sh shutdown を実行。セクション G のタイミング依存の SSD ロードに必要 — ショー APK は SSD 接続済みの状態で起動した直後にのみコピー処理を起動します。
Wait for each device's fan to stop
Don't attach SSDs or proceed while the Compute Pack fan is spinning.
各デバイスのファンが停止するまで待つ
Compute Pack のファンが回っている間は SSD を接続したり次の作業に進まないでください。
G · Load BLUE show assets per device via SSD G・SSD から各デバイスへ BLUE ショーアセットを転送
One device at a time — order is strict
Always: attach SSD → power on device → put on headset → listen. The show APK looks for the SSD at launch; missing the window means the copy doesn't start.
1台ずつ作業 — 順序を厳守
常に SSD 接続 → デバイス電源オン → ヘッドセット装着 → 音を聞く。ショー APK は起動時にのみ SSD を検出。タイミングを逃すとコピーは開始しません。
Attach the BLUE SSD before powering on
USB-C SSD with the BLUE asset payload. Plug into the Compute Pack while the device is still off.
起動前に BLUE 用 SSD を接続
BLUE アセットが入った USB-C SSD を、デバイスがオフの状態のまま Compute Pack に接続。
Power on, put on headset, listen for start tones
Hold Power. The kiosk + show APK launch. A start tone series plays when copy begins.
電源オン、ヘッドセット装着、開始音を聞く
電源 を長押し。キオスクとショー APK が起動。コピー開始時に開始音のシリーズが鳴ります。
Wait for the finish tone series
Second tone series = copy complete. Safe to remove the SSD only after the finish tones.
No tones within ~30s of boot? Timing window missed. Shut down, re-attach SSD, power on again.
終了音が鳴るまで待つ
終了音が鳴ったらコピー完了。これを聞いてから SSD を外してください。
起動から約30秒経っても音が鳴らない場合はタイミング失敗。シャットダウン → SSD 再接続 → 再起動でやり直してください。
Remove SSD, leave device powered on
Detach SSD. Device stays on for the final dashboard sweep in Section H.
SSD を外し、デバイスは起動したまま残す
SSD を取り外します。セクション H の最終ダッシュボード取得のため、電源は入れたままにしてください。
Repeat across operators
~200 functional devices × ~3 minutes per device. With multiple SSDs (one per operator), 8 stations finish in ~75 minutes of device-time.
複数オペレーターで繰り返し
約200台 × 約3分。SSD を複数（1 オペレーター 1 台）用意し、8 ステーション並列で約75分（実時間）で完了見込み。
H · Verify the BLUE fleet is show-ready H・BLUE フリートのショー本番準備完了を確認
Re-run the status sweep
./ml_status.sh --json > status/latest.json, reload fleet_dashboard.html.
ステータススイープを再実行
./ml_status.sh --json > status/latest.json を実行し、fleet_dashboard.html を再読み込み。
Confirm data-folder rows are clean
Devices that completed the SSD copy should no longer flag "data missing". Disk usage rises — that's expected.
データフォルダ行がクリーンになっていることを確認
SSD コピーが完了したデバイスは「data missing」フラグが消えるはず。ディスク使用量増加は想定どおり。
Report to supervisor
Note All-OK / Issues / Offline counts, any stubborn red IPs, and hand the dashboard view to the supervisor. They decide go / no-go.
スーパーバイザーに報告
All-OK・Issues・Offline 件数、しつこく赤のままの IP を記録し、ダッシュボードをスーパーバイザーに引き継ぎます。本番可否はスーパーバイザーが判断。
BLUE fleet is show-ready.
BLUE フリート、本番準備完了。
